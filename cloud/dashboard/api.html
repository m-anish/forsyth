Start here

One base URL, no key, no sign-up, no terms to accept. Everything below is a plain GET that returns JSON.

curl https://live.forsyth.starstucklab.com/api/v1/stations

That lists every station with its latest reading. From there, the two calls that do most of the work:

# the last six hours of temperature and humidity, as a time series
curl "https://live.forsyth.starstucklab.com/api/v1/stations/leaf-01/series?metrics=temp_c,rh&hours=6"

# a week of everything, as a CSV you can open in a spreadsheet
curl -o week.csv "https://live.forsyth.starstucklab.com/api/v1/export/leaf-01.csv?hours=168"
try it, from this page

The response appears here, fetched by your own browser from the same public API — no proxy, no key.

The stations

A station is identified by its slug, which is what goes in a URL. This list is read from the API when you load this page, so it is the real one:

These are small solar-powered stations in the Dhauladhar foothills, reporting every few minutes over LoRa. They are not a professional network: a station can be offline for a day because it was cloudy, and a sensor can be wrong. The dashboard shows what each one is doing right now, and /api/v1/health says the same thing in JSON.

Endpoints

All of these are public. Anything not listed here needs a sign-in, and you may ignore it. {slug} is a station slug from the list above.

pathwhat it gives you
/api/v1/stations Every station: name, coordinates, elevation, and its most recent reading.
/api/v1/stations/{slug}/latest The single newest reading, every field, unaggregated.
/api/v1/stations/{slug}/series A time series. ?metrics= comma-separated field names, ?hours= up to 8784 (a year). Returns {ts: [...], series: {field: [...]}, bucket: "5 minutes"} — arrays line up by index, and null means no reading, not zero.
/api/v1/stations/{slug}/windrose 16 compass bins × 4 speed bands over ?hours=, plus the share of the time it was calm.
/api/v1/stations/{slug}/forecast The latest model run for that station's exact coordinates, ?hours= up to 168. Includes ensemble spread where the GEFS rows exist.
/api/v1/stations/{slug}/skill How wrong those forecasts have been, verified against this station's own readings, bucketed by lead time. ?days= up to 365.
/api/v1/stations/{slug}/frames/latest The newest camera frame, if that station has a camera: {ts, url}. The URL is under /media/.
/api/v1/stations/{slug}/timelapses Up to 60 days of daily timelapse videos.
/api/v1/lightning Strikes across the mesh, ?hours= and optional ?slug=. Distance in km, as the sensor estimated it.
/api/v1/stations/{slug}/river Modelled river discharge for the nearest reaches, with each reach's own warning and danger thresholds. Modelled, not measured — there is no river gauge in this valley, so these are Google's virtual HydroBASINS reaches and none of them is quality-verified. of_warning is the only figure comparable between reaches; raw discharge is not, because warning levels here span 17.7 to 1781 m³/s.
/api/v1/health Per station: last heard, battery, radio signal, and whether it has gone stale. This is what you would poll to notice an outage.
/api/v1/reports Weather reported by people rather than sensors, ?hours=. Locations are rounded to roughly 100 m on purpose.
/api/v1/alerts Current alert level per station and for the mesh as a whole.
/api/v1/summary The plain-English banner the dashboard shows, and the events behind it.
/api/v1/export/{slug}.csv Bulk history — see below.

The machine-readable schema for all of it, with every parameter and response shape, is at /api/docs (openapi.json). It is generated from the code, so it is never out of date — it also lists the write endpoints, which will refuse you.

What the numbers mean

Field names are the same everywhere — in /latest, in ?metrics=, and as CSV column headers.

fieldunit — and the catch, where there is one
temp_c°C
rh% relative humidity
pressure_pa Pascals, as measured at the station — not reduced to sea level. At 1676 m that reads around 83,800 Pa, which is not a broken barometer. The dashboard reduces it before display; if you want a number comparable with a weather report, you must do the same, and you will need the station's elevation_m from /stations.
wind_avg_msm/s, averaged over the reporting interval
wind_gust_msm/s, the peak in that interval
wind_dir_deg degrees, 0 = north, clockwise. Below about 0.5 m/s a stationary vane points wherever it was last pushed, so treat the direction as meaningless when the speed is near zero — the wind rose discards those samples rather than counting them.
rain_mm mm in that interval, not a running total. Summing is correct; averaging is not. /series sums it per bucket while averaging everything else.
pm1, pm25, pm10 µg/m³. Sampled far less often than the rest — roughly every half hour — so expect long runs of null between real values.
batt_vvolts, LiFePO4, rested
rssi_dbmdBm, the LoRa link as the gateway heard it
solar_statea string, not a number — so it cannot be asked for in ?metrics=

Timestamps are UTC throughout. /series returns them as epoch seconds; everything else uses ISO 8601. The stations are in India (UTC+05:30), so a "day" in the data is not a local day unless you shift it.

How /series buckets

The window decides the resolution, because a year at one-minute resolution helps nobody:

?hours=bucket
up to 121 minute — as fine as the stations actually report
up to 485 minutes
up to 336 (14 days)1 hour, from the hourly rollup
beyond that1 day

The response tells you which you got, in bucket. If you want full resolution over a long window, use the CSV instead — it is not bucketed.

Bulk history

One row per report, every field, no aggregation. Either a window back from now, or explicit dates. all in place of a slug gives every station in one file with a station column.

# thirty days from one station
curl -o leaf.csv "https://live.forsyth.starstucklab.com/api/v1/export/leaf-01.csv?hours=720"

# a named range, every station
curl -o all.csv "https://live.forsyth.starstucklab.com/api/v1/export/all.csv?start=2026-09-01&end=2026-10-01"

Ranges are capped at 366 days. If you want more than that, make several calls — or ask, and you can have a database dump instead of hammering this one.

Limits

No key, but not unlimited: this runs on a single small virtual machine in Bangalore, and one script in a retry loop can take the site away from everybody else.

  • 300 requests a minute per address for everything.
  • 10 a minute for CSV exports, which are the expensive ones.

Over either, you get 429 with a Retry-After header saying how many seconds to wait. Honour it and you will never see another one. Those numbers are set where they are because the dashboard itself costs 38 calls to load a page — if you need more than a person browsing, say so rather than working around it.

Two things that will keep you well inside them: readings arrive every few minutes, so polling faster than once a minute only burns your budget; and if you want history, one CSV beats a thousand calls to /series.

From a browser

Reads are open to every origin, so you can fetch this directly from a page of your own — no proxy, no server in the middle. GET and HEAD only, and no credentials, which is how it stays safe to leave open.

const BASE = 'https://live.forsyth.starstucklab.com/api/v1';

const { stations } = await (await fetch(`${BASE}/stations`)).json();
console.log(stations.map(s => `${s.name}: ${s.temp_c}°C`));

// a time series, arrays aligned by index
const d = await (await fetch(
  `${BASE}/stations/leaf-01/series?metrics=temp_c&hours=24`)).json();
const points = d.ts.map((t, i) => ({
  at: new Date(t * 1000),
  tempC: d.series.temp_c[i],          // null where there is no reading
})).filter(p => p.tempC !== null);

Live push

There is an MQTT broker behind this — it is how the hardware reports — but it is not open for subscription, and saying otherwise would be doing you a disservice: it has no per-topic access control yet, so a credential that can read can also publish, and a credential that can publish can rewrite any station's position. Opening it properly means ACLs, TLS and a websockets listener, and until that exists the honest answer is "poll the API".

Once a minute is plenty — readings do not arrive faster than that. If you are building something that genuinely needs push, open an issue and it will move up the list.

Terms

The readings are published under Creative Commons Attribution 4.0. Use them, republish them, sell what you build on them, train something on them, change them — commercially or not. The one condition is that you say where they came from.

Saying where they came from

Anything that credits the source, links back, and names the licence will do. This, for instance:

Weather data from the Forsyth mesh (Bir, Himachal Pradesh)
https://live.forsyth.starstucklab.com — CC BY 4.0

On a chart, a line of small print under it is plenty. In a dataset, a line in the README. Machine-readable too: every API response carries a Link: <…>; rel="license" header pointing at the same licence.

Worth knowing, since it cuts both ways: in much of the world a raw measurement is a fact, and facts are not copyrightable. So over a single reading this licence may have nothing to bite on, and over a whole database it may — depending on where you are. Treat the attribution clause as what is being asked of you rather than as a threat; it is here so that a chart somewhere can be traced back to a hillside, not to generate correspondence.

What it does not cover

Forecasts served from /forecast are Open-Meteo's model output, not ours, and carry their terms. Map tiles belong to whoever drew them — each is credited on the map itself. River reaches from /stations/{slug}/river are Google Flood Hub's — also CC BY 4.0, so you may reuse them, but the attribution you owe for those is Google's rather than ours. Camera frames are ours and under the same CC BY 4.0 as the readings, as are the verification numbers from /skill — those are computed here, from our own readings. The code is MIT, separately. The full breakdown is in DATA-LICENSE.md.

And a request that is not a licence condition

Do not pretend these are something they are not. They come from homemade stations on a hillside, maintained by one person. Do not present them as official observations, and do not use them where being wrong matters — aviation, say, or anything load-bearing. Each station's /skill endpoint will tell you honestly how far off its forecasts have been; the sensors deserve the same scepticism. If something here is wrong or missing, the fastest fix is a pull request.
